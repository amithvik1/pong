## 1. `game/config.py` — the shared constants

**Path:** `game/config.py` · 33 lines · `[IMPORT]` by 6 modules
(`game/protocol.py`? no — by `game/state.py`, `game/server.py`, `game/client.py`, `game/menu.py`,
`sdn/qos_switch.py`, `topo/topology.py`, `topo/scenarios.py`).

### What it does
Holds every number that more than one component must agree on.

### How it works
It is **deliberately import-free and syntax-3.9-clean**. The docstring says so:

> *"Imported by the game, the Mininet scripts and (later) the Ryu controller, so the UDP port and
> timing values live in exactly one place. Keep this file free of imports and of syntax newer than
> Python 3.9 (the Ryu environment is 3.9)."*

### Key settings
- `GAME_PORT = 5000` — the UDP port. **The single most important constant in the project**, because
  it is simultaneously (a) where the game server listens, (b) where clients send, and (c) the
  OpenFlow match field that identifies "game traffic" to the SDN controller.
- `TICK_HZ = 30` — used by the server as the simulation rate, by the client as the input-send
  rate, and by `topo/topology.py:315` as the expected broadcast rate in the smoke test.
- `MAX_PLAYERS = 4` — also the width of every tuple in `Snapshot` (`paddles`, `lives`, `active`).
- `NO_PLAYER = 0xFF` — sentinel in `JOIN_ACK.player_id` meaning "server full". The client raises
  `JoinError("server is full")` when it sees it (`client.py:103-104`).
- `QUEUE_GAME = 1` / `QUEUE_BG = 2` — the OVS queue IDs. Used by `sdn/qos_switch.py` to emit
  `set_queue` actions, and by `topo/topology.py:169-174` to create the HTB classes.
- Game physics: `LIVES=3`, `PADDLE_LEN=0.20`, `PADDLE_SPEED=0.90`, `BALL_RADIUS=0.02`,
  `BALL_SPEED=0.45`, `BALL_SPEEDUP=1.04`, `BALL_MAX_SPEED=0.90`, `SERVE_DELAY=1.0`,
  `GAME_OVER_DELAY=3.0`.

### Inputs / outputs
No inputs. Its "output" is the module namespace that other files do `from . import config as C`.

### Dependencies
**None.** This is deliberate: it is the one file that the Ryu controller (which runs in a separate
Python 3.9 virtualenv) is allowed to import.

### Suspicious / noteworthy
- The `PADDLE_SPEED`, `BALL_SPEED` etc. are "arena units per second" where the arena is the unit
  square `[0,1] x [0,1]`. At `BALL_SPEED = 0.45`, a ball takes roughly 2.2 s to cross the arena
  diagonally. That is a *slow, readable* Pong — appropriate for a terminal demo, not for a twitch
  game.
- `PLAYER_TIMEOUT = 3.0` s vs. `PING_INTERVAL = 1.0` s: a client sends an update every ~33 ms, so
  3 s of silence is ~90 missed updates. Generous, and it means a player who closes the TUI
  gracefully (sends `LEAVE`) leaves instantly, while a crashed client is cleaned up within 3 s.
- **No bug.** The file is correct.

## 2. `game/protocol.py` — the wire format

**Path:** `game/protocol.py` · 169 lines · `[IMPORT]` by `game/server.py`, `game/client.py`,
`game/state.py`, `game/bot.py`, `game/tui.py`, `tests/test_protocol.py`.

### What it does
Defines exactly how a byte stream becomes a game message, and validates that a received byte
stream is a legitimate message.

### How it works — the packet layout

Every packet is a **15-byte header** followed by a **fixed-size payload**:

```
byte 0      version    u8    (always 1)
byte 1      type       u8    (1..7, see below)
byte 2..5   seq        u32   big-endian sequence number within its stream
byte 6..13  send_time  f64   time.monotonic() at the sender
byte 14     player_id  u8    slot 0..3 involved in the message
```

`HEADER = struct.Struct("!BBIdB")` — the `!` means **network byte order (big-endian)**, no padding.
`tests/test_protocol.py::test_header_size` asserts `HEADER.size == 15`.

### The seven message types

| Constant | Value | Payload | Meaning |
|---|---|---|---|
| `JOIN` | 1 | empty | "I want to play" |
| `JOIN_ACK` | 2 | empty | `player_id` = assigned slot, or `NO_PLAYER` (0xFF) if full |
| `STATE_UPDATE` | 3 | `i8` direction | Client → server: my paddle direction (-1/0/+1) |
| `STATE_BROADCAST` | 4 | 40 bytes | Server → all: the whole world |
| `PING` | 5 | empty | Client → server: RTT probe |
| `PONG` | 6 | `f64` echo | Server → client: echoes the PING's `send_time` |
| `LEAVE` | 7 | empty | Client → server: I am going |

`BROADCAST = struct.Struct("!IB2f4f4B4B")` = `tick(u32) phase(u8) ball_x(f32) ball_y(f32)
paddles(4×f32) lives(4×u8) active(4×u8)` = 4+1+8+16+4+4 = **37 bytes**? Let's verify:
`!` = no alignment, so `I`=4, `B`=1, `2f`=8, `4f`=16, `4B`=4, `4B`=4 → **37 bytes**.
Total broadcast packet = 15 + 37 = **52 bytes**.

### The "stream" concept — this is the subtle part

The docstring explains it, and it is worth understanding because it is the key to the loss
accounting being correct:

> *"A stream is one sender + one message type, each with its own counter: client → server
> STATE_UPDATE (one stream per client); client → server PING (separate counter, so it never
> creates gaps in the STATE_UPDATE stream); server → clients STATE_BROADCAST (one global counter);
> server → client PONG."*

**Why it matters:** if PING shared the STATE_UPDATE counter, then a lost PING would look like a
lost STATE_UPDATE, and the loss statistics would be wrong. Because each has its own counter, the
`SeqTracker` attached to each player measures exactly one thing: "how many of *your* state
updates did I miss?"

**Consequence:** the client keeps **one** tracker for the server's broadcast stream
(`client.py:55`), and the server keeps **one tracker per player** for that player's update stream
(`server.py:38`).

### The `send_time` field and the shared clock

> *"`send_time` uses the monotonic clock. Every Mininet host runs on the same kernel, so it is one
> shared clock and `recv_time - send_time` is a true one-way delay. (It would NOT be meaningful
> between two physical machines.)"*

This is an **important limitation** and it is correctly documented in the source. `time.monotonic()`
is *per-process/per-kernel*; two physical laptops have unrelated monotonic clocks. So the one-way
delay numbers in `results/` are only meaningful **inside the Mininet VM** (or on one machine).
**Do not quote the delay numbers from a two-laptop demo** — use the RTT numbers, or just
demonstrate that the game works.

### Validation — `decode()`

```python
def decode(data: bytes) -> Tuple[Header, bytes]:
    if len(data) < HEADER.size:        raise ProtocolError("short packet")
    version, msg_type, seq, send_time, player_id = HEADER.unpack_from(data)
    if version != VERSION:              raise ProtocolError("unsupported version")
    if msg_type not in TYPE_NAMES:      raise ProtocolError("unknown message type")
    payload = data[HEADER.size:]
    if len(payload) != PAYLOAD_SIZE[msg_type]:
                                        raise ProtocolError("... payload is N bytes, expected M")
    return Header(...), payload
```

Four independent checks. This is what makes the server robust against garbage on the wire, and
`tests/test_loopback.py::test_server_survives_garbage` fires 50 random 30-byte packets plus an
empty one at the server and asserts `bad_packets >= 40` while the server keeps serving normally.

### Other functions
- `now()` → `time.monotonic()`.
- `encode(msg_type, seq, player_id=0, payload=b"", send_time=None)` — `send_time` defaults to
  `now()`; `seq` is masked with `SEQ_MASK = 0xFFFFFFFF` so it wraps cleanly.
- `pack_update(direction)` clamps to [-1, 1]; `unpack_update` clamps again on the way in.
- `pack_broadcast(snapshot)` / `unpack_broadcast(payload)` → `Snapshot` dataclass.
- `Snapshot` is a `@dataclass` (not frozen) with `tick, phase, ball_x, ball_y, paddles, lives,
  active`.

### Suspicious / noteworthy
- `PHASE_WAITING = 0`, `PHASE_PLAYING = 1`, `PHASE_GAME_OVER = 2` are defined here rather than in
  `state.py`, which is slightly odd for a "game concept" constant — but it is defensible, because
  `phase` is a **wire field** and the client must know its meaning.
- `from __future__ import annotations` is used, so the `Tuple[Header, bytes]` annotations are lazy.
  Fine on 3.9.
- **No bug.** The file is clean and thoroughly tested.

## 3. `game/seq.py` — the sequence-number tracker

**Path:** `game/seq.py` · 82 lines · `[IMPORT]` by `game/server.py`, `game/client.py`,
`tests/test_protocol.py` (`SeqTrackerTests`).

### What it does
Decides, for every packet that arrives, one of four things: **new**, **duplicate**, **late**, or
**stale**. This is the file that makes UDP safe for a real-time game.

### The four verdicts

| Constant | Meaning | What the game should do |
|---|---|---|
| `NEW` | Higher than anything seen so far | **Apply it** |
| `DUPLICATE` | Already received | Ignore |
| `LATE` | Arrived out of order, but fills an earlier gap | Ignore for state (but count as received) |
| `STALE` | Too old to even classify | Ignore |

### How it works — the bitmask trick

The tracker keeps one integer, `self._mask`, as a **sliding window of 64 bits**:

```
bit i set  <=>  sequence number (highest - i) was received
```

`observe(seq)` (`seq.py:42-68`) does this:

```python
if self.highest is None:          # first packet ever
    self.first = self.highest = seq
    return NEW, 0

if seq > self.highest:            # the normal case
    shift = seq - self.highest
    self._mask = 1 if shift >= WINDOW else ((self._mask << shift) | 1) & full
    self.highest = seq
    self.received += 1
    return NEW, shift - 1          # gap = how many we skipped

delta = self.highest - seq
if delta >= WINDOW:               # fell off the back of the window
    self.stale += 1
    return STALE, 0

bit = 1 << delta
if self._mask & bit:              # already seen this one
    self.duplicates += 1
    return DUPLICATE, 0

self._mask |= bit                 # fills an earlier gap
self.received += 1
self.late += 1
return LATE, 0
```

**The `gap` return value** (the second item of the tuple) is how many sequence numbers were
skipped just before a `NEW` packet. It is the raw loss signal.

### The loss maths

```python
@property
def expected(self):  return self.highest - self.first + 1
@property
def lost(self):      return max(0, self.expected - self.received)
@property
def loss_ratio(self): return self.lost / self.expected if self.expected else 0.0
```

**Why this is exactly right, not approximate:** `received` counts `NEW` **plus** `LATE`. A late
packet that fills a gap *was* received, so it must not be counted as lost. Only packets that
never arrived at all stay in the `lost` count.

**One subtlety worth knowing:** packets **before the first one we ever saw** are not counted as
lost. A client that joins mid-stream would otherwise show a huge fake loss. The `first` field
is what prevents that.

### Suspicious / noteworthy
- The `WINDOW = 64` constant means a packet more than 64 sequences behind the highest is
  classified `STALE` rather than `DUPLICATE` or `LATE`. At 30 Hz that is about 2 seconds of
  history — plenty for a LAN, and it keeps the mask a single machine word.
- `first` is never used to compute loss except through `expected`. It exists purely to stop the
  "joined mid-stream" false positive.
- **No bug.** This file is the cleanest piece of logic in the project.

## 4. `game/state.py` — the pong simulation

**Path:** `game/state.py` · 181 lines · `[IMPORT]` by `game/server.py`, `game/menu.py`,
`tests/test_state.py`.

### What it does
The actual game. **Pure logic: no sockets, no threads, no clock.** The server calls
`state.step(dt)` 30 times a second and the state moves. That separation is why the whole game
is testable without a network.

### The arena

The arena is the **unit square** `[0,1] x [0,1]`.

| Slot | Wall | Paddle moves along | Your keys |
|---|---|---|---|
| 0 | left | y | `W`/`S` or `↑`/`↓` |
| 1 | right | y | `W`/`S` or `↑`/`↓` |
| 2 | top | x | `A`/`D` or `←`/`→` |
| 3 | bottom | x | `A`/`D` or `←`/`→` |

Input is `-1` (toward 0, i.e. up/left), `0` (stop) or `+1` (toward 1, i.e. down/right).

### The three phases

```
WAITING ──(2 or more active players)──▶ PLAYING ──(1 or 0 alive)──▶ GAME_OVER
   ▲                                                                        │
   │◀──────(fewer than 2 active)───────────────────────────────────────────┘
                    GAME_OVER ──(timer expires, 2+ active)──▶ new PLAYING game
```

| Phase | Constant | What happens |
|---|---|---|
| Waiting | `PHASE_WAITING = 0` | Ball parked in the centre. Starts the game the moment 2 players are active (`state.py:60-63`). |
| Playing | `PHASE_PLAYING = 1` | Normal play. |
| Game over | `PHASE_GAME_OVER = 2` | Ball parked, winner recorded, waits `GAME_OVER_DELAY = 3.0` s, then **restarts automatically** if 2+ players remain. |

**Why the auto-restart matters:** the traffic must not stop during a measurement. If the game
sat still for 3 s every round, the delay graphs would have holes. This is a deliberate
experiment-friendly choice, and the docstring says so.

### The collision maths — `_wall_hit`

This is the most interesting function in the file (`state.py:135-168`).

```python
alive = self.active[slot] and self.lives[slot] > 0
reach = C.PADDLE_LEN / 2 + C.BALL_RADIUS
if alive and abs(coord - self.paddles[slot]) > reach:
    self.lives[slot] -= 1      # missed -> lose a life
    self._serve()              # and re-serve from the centre
    return True
```

**An empty or eliminated slot's wall is solid.** The ball just bounces off it. Only a *live*
player's paddle can miss.

**When the paddle does hit**, two things happen:

1. **Speed up:** `self.speed = min(self.speed * BALL_SPEEDUP, BALL_MAX_SPEED)` — 4 % faster per
   hit, capped at 0.90.
2. **Spin:** where on the paddle you hit decides the outgoing angle.

```python
offset = (coord - self.paddles[slot]) / (C.PADDLE_LEN / 2)   # -1 .. +1
spin = offset * 0.5 * self.speed
```

Then the new velocity is computed so the **total speed is preserved**:

```python
vt = max(-0.85 * s, min(0.85 * s, self.vy + spin))   # clamp the tangential part
self.vx = sign * math.sqrt(s * s - vt * vt)           # Pythagoras for the normal part
self.vy = vt
```

That `sqrt(s*s - vt*vt)` line is the classic billiard reflection: the tangential component is
kept, the normal component is recomputed from the remaining speed. The `0.85` clamp stops the
ball going nearly perpendicular to the wall.

### The serve

```python
angle = math.radians(self.rng.choice((45, 135, 225, 315)) + self.rng.uniform(-25, 25))
```

A random diagonal direction (never straight along an axis, so it always looks like a real
rally), plus up to ±25° of jitter. `SERVE_DELAY = 1.0` s of pause before the ball moves, so
players can get ready.

### Dependencies
`math`, `random`, `game/config.py`, and three phase constants + the `Snapshot` dataclass from
`game/protocol.py`.

### Suspicious / noteworthy
- **`self.rng = random.Random(seed)`** — the state has its own RNG, so a seeded game is
  **fully reproducible**: the same serve angles, the same order. The server passes `seed` through
  to it (`server.py:56`).
- The ball's speed is in "arena units per second". At `BALL_SPEED = 0.45` it crosses the arena
  in roughly 2.2 s. **A slow, readable Pong** — right for a terminal demo, wrong for a twitch
  game, and correct for this project.
- `_move_ball` checks one wall per call and `return`s after a hit. It does not re-check the
  other three axes in the same tick. At 30 Hz with a maximum speed of 0.90 the ball moves at
  most 0.03 arena units per tick, so it can never tunnel through a wall. **Not a bug** — but it
  is worth knowing if you ever raise the tick rate or the speed.
- **No bug found.** The file is correct and is covered by 11 tests.

## 5. `game/bot.py` — the computer player

**Path:** `game/bot.py` · 37 lines · `[IMPORT]` by `game/menu.py`, `game/client.py`,
`tests/test_bot.py`.

### What it does
Moves a paddle. That is the whole job.

**The important design point:** the bot has the **same interface as a human**. The client calls
`self.input_fn(snapshot, player_id)` and gets back `-1`, `0` or `+1`. A human's
`HumanInput` returns exactly the same thing. So the bot is a **drop-in replacement for the
keyboard**, not a special kind of player in the protocol.

### How it works

```python
def __call__(self, snap, slot) -> int:
    if snap is None or snap.phase != PHASE_PLAYING:
        return 0                                    # not playing -> do nothing
    if not snap.active[slot] or snap.lives[slot] <= 0:
        return 0                                    # dead or not in -> do nothing

    bucket = snap.tick // REROLL_TICKS
    if bucket != self._bucket:                     # re-pick the error every 0.6 s
        self._bucket = bucket
        self._offset = self.rng.uniform(-self.error, self.error)

    ball = snap.ball_y if slot < 2 else snap.ball_x # where the ball is along MY wall
    diff = (ball + self._offset) - snap.paddles[slot]
    if abs(diff) < DEADBAND:                       # 0.02 - do not jitter
        return 0
    return 1 if diff > 0 else -1
```

| Constant | Value | Why |
|---|---|---|
| `DEADBAND` | 0.02 | Stops the bot from jittering when it is already lined up. In arena units that is 2 % of the wall. |
| `REROLL_TICKS` | 18 | Re-picks the aiming error every 18 ticks = 0.6 s at 30 Hz. If the error were re-picked every tick the bot would be aimless; if it were never re-picked, the bot would drift consistently off-centre and always lose the same way. |

### The skill levels

`game/menu.py:30`:

```python
SKILLS = (("easy", 0.32), ("normal", 0.14), ("hard", 0.03))
```

The number is the **maximum aiming error in arena units** (half the paddle length is 0.10). So
`easy = 0.32` means the bot can aim up to 3.2 paddle-lengths away from the ball — it will miss
a lot. `hard = 0.03` means it barely misses at all.

**`error=0` gives a perfect bot** — the constructor says so explicitly. Useful for testing.

### Reproducibility
`Bot(seed=N)` uses its own `random.Random(seed)`, so a seeded bot behaves identically on every
run. That is what makes `--seed N` in `game/client.py` reproducible.

### Suspicious / noteworthy
- The bot follows the ball **along its own wall only** (`snap.ball_y` for slots 0/1,
  `snap.ball_x` for slots 2/3). It has no idea where the ball is in the other dimension, so it
  does not "line up" for a diagonal shot. A slightly smarter bot would project the ball's path
  to the wall. **Not a bug — a possible improvement.**
- The bot does not use the `phase` field of the snapshot beyond the "am I playing" check, and
  it never looks at the ball's velocity.
- **No bug.** Clean, small, well-tested (9 tests).

## 6. `game/signals.py` — clean shutdown

**Path:** `game/signals.py` · 13 lines · `[IMPORT]` by `game/server.py`, `game/client.py`.

### What it does
One function, `exit_on_signals()`, that makes `SIGTERM` behave like `Ctrl-C`.

```python
def exit_on_signals() -> None:
    def handler(signum, frame):
        raise KeyboardInterrupt

    signal.signal(signal.SIGTERM, handler)
    signal.signal(signal.SIGINT, handler)
```

### Why it matters

**`SIGTERM` is what `kill <PID>` sends.** By default, `SIGTERM` kills a Python process
immediately — the `finally:` blocks do **not** run. That means:

- the CSV log file is **not flushed** (the last rows are lost),
- the client does **not** send its `LEAVE` packet,
- the server keeps the player slot occupied for the full 3-second timeout.

Turning `SIGTERM` into `KeyboardInterrupt` means the normal `Ctrl-C` cleanup path runs
instead. That is what `topo/topology.py` relies on when it stops the game server and the bots.

### The second line is the clever part

```python
# Also re-enables Ctrl-C if this process inherited "ignore SIGINT"
# (which happens for background jobs started by a non-interactive shell).
signal.signal(signal.SIGINT, handler)
```

When a shell starts a background job, the child inherits `SIGINT` set to **ignore**. A child
that inherits "ignore" cannot be interrupted by `Ctrl-C` — and, on some systems, cannot
re-enable it at all. Calling `signal.signal(SIGINT, handler)` explicitly **re-enables** it.

**Practical effect:** `Ctrl-C` in the Mininet CLI, or `kill` on the topology's processes, stops
the game server and the bots **cleanly**, with the logs flushed.

### Suspicious / noteworthy
- The handler takes `signum` and `frame` but ignores both. That is correct — it just raises.
- `signal.signal` only works in the **main thread**. If `exit_on_signals()` were called from a
  worker thread it would raise `ValueError`. It is called from `main()` in both server and
  client, so this is fine.
- **No bug.** Thirteen lines that solve a real problem.

## 7. `game/server.py` — the authoritative game server

**Path:** `game/server.py` · 235 lines · `[EXEC]` as `python3 -m game.server`.

### What it does
Holds the real game state, registers players, advances the simulation, and broadcasts the world
to everyone, 30 times a second.

### The two threads

The docstring says it plainly:

```
Two threads, as in the design:
  * receive thread  - parses packets, registers/removes players, stores each
                      player's latest input (only if its seq is newer)
  * tick thread     - every 1/TICK_HZ s: evict silent players, advance the
                      simulation, broadcast the whole world to every player
```

**Plus a lock.** `self.lock = threading.Lock()` guards `self.players` and `self.state`. Both
threads take it. This is the only synchronisation in the whole project, and it is enough.

### The player table — `Player`

```python
class Player:
    def __init__(self, slot, addr, t):
        self.slot = slot                 # 0..3, which wall
        self.addr = addr                 # (ip, port) — the UDP return address
        self.last_seen = t               # for the timeout check
        self.tracker = SeqTracker()      # THIS player's STATE_UPDATE stream
```

**One tracker per player** is the key detail. The server measures "how many of *your* updates
did I miss?" separately for each client. The protocol's "one stream per sender per message
type" design (see `game/protocol.py`) makes this exact.

### The socket

```python
self.sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
self.sock.bind((host, port))            # host defaults to "0.0.0.0"
self.sock.settimeout(0.2)               # so the loop can check the stop flag
```

| Line | Why |
|---|---|
| `AF_INET, SOCK_DGRAM` | UDP over IPv4. No TCP anywhere. |
| `bind((host, port))` with `host="0.0.0.0"` | Accept on **every** interface, so other laptops can join. |
| `settimeout(0.2)` | The recv loop wakes up 5×/s to check `self._stop`. Without it, `Ctrl-C` would not be noticed until the next packet arrived. |

### The receive path

```python
def _recv_loop(self):
    while not self._stop.is_set():
        try:
            data, addr = self.sock.recvfrom(2048)
        except socket.timeout:
            continue
        except OSError:
            break
        if self.drop_prob and self._loss_rng.random() < self.drop_prob:
            self.dropped += 1
            continue
        t_recv = P.now()
        try:
            hdr, payload = P.decode(data)
        except P.ProtocolError:
            self.bad_packets += 1
            continue
        with self.lock:
            self._handle(hdr, payload, addr, t_recv)
```

**Five layers of protection in nine lines:**

1. `recvfrom(2048)` — a 2048-byte buffer, so an oversized packet is truncated, not fatal.
2. `except OSError: break` — the socket was closed (shutdown) → leave the loop.
3. **The `--drop` test hook** — randomly discards a fraction of packets *before* they are
   decoded. This is how loss is injected for testing. The RNG is seeded
   (`self._loss_rng = random.Random(loss_seed)`), so it is **reproducible**.
4. `P.decode()` validates the packet. A `ProtocolError` increments `bad_packets` and is
   ignored. This is what makes the server survive garbage on the wire.
5. `with self.lock:` — the only place the shared state is touched.

### The message handler — `_handle`

```python
def _handle(self, hdr, payload, addr, t_recv):
    player = self.players.get(addr)
    if player:
        player.last_seen = t_recv         # ANY message refreshes the timeout

    if hdr.msg_type == P.JOIN:
        if player is None:
            slot = self._pick_slot()      # lowest free slot, or NO_PLAYER
            if slot == C.NO_PLAYER:
                self._send(addr, P.encode(P.JOIN_ACK, 0, C.NO_PLAYER))
                return
            player = Player(slot, addr, t_recv)
            self.players[addr] = player
            self.state.set_active(slot, True)
            log.info("player %d %s", slot, reason)
            self.on_join(player)          # <-- D2 STUB (see below)
        self._send(addr, P.encode(P.JOIN_ACK, 0, player.slot))   # idempotent

    elif hdr.msg_type == P.STATE_UPDATE and player:
        kind, _gap = player.tracker.observe(hdr.seq)
        if kind == NEW:                   # old/duplicate/late updates are ignored
            self.state.set_input(player.slot, P.unpack_update(payload))
        if self._log_csv:
            self._log_csv.writerow([...])

    elif hdr.msg_type == P.PING:
        self._send(addr, P.encode(P.PONG, self._pong_seq, player.slot if player else 0,
                                  P.pack_echo(hdr.send_time)))
```

**Four things worth pointing out:**

1. **`last_seen` is refreshed by any message**, not just `STATE_UPDATE`. So a client that only
   sends `PING` is still considered alive.
2. **The `JOIN` handler is idempotent.** A repeated `JOIN` from a known address re-sends the
   same `JOIN_ACK` with the same slot. That is how the client's retry logic works — it can
   retry blindly and still end up in the right place.
3. **Only `NEW` updates change the state.** This is "latest state wins" on the server side.
4. **The `PING` handler echoes the client's `send_time` back** in the `PONG` payload. That is
   how the client computes the RTT without needing synchronised clocks.

### The tick path — `_tick_loop`

```python
def _tick_loop(self):
    dt = 1.0 / self.tick_hz
    next_t = time.monotonic()
    while not self._stop.is_set():
        next_t += dt
        with self.lock:
            t = P.now()
            for p in [p for p in self.players.values() if t - p.last_seen > self.player_timeout]:
                self._remove(p, "timed out")
            self.state.step(dt)
            seq = self._bcast_seq
            self._bcast_seq += 1
            pkt = P.encode(P.STATE_BROADCAST, seq, 0, P.pack_broadcast(self.state.snapshot()))
            addrs = list(self.players)
        for addr in addrs:
            self._send(addr, pkt)
        delay = next_t - time.monotonic()
        if delay > 0:
            self._stop.wait(delay)
```

**The important design choice:** the lock is released **before** the packets are sent. Sending
30 packets × 4 players = 120 `sendto` calls per tick, and doing that while holding the lock
would stall the receive thread. The address list is copied under the lock, then used outside it.

**The timing is absolute, not relative.** `next_t += dt` (rather than "sleep dt") means the
tick rate does not drift. If the loop is delayed, it catches up instead of falling behind.
`self._stop.wait(delay)` sleeps with a timeout, so `Ctrl-C` is noticed immediately.

**The order inside the tick:** evict silent players → step the simulation → build the broadcast
→ send. So a player who just timed out does not get one more broadcast.

### The D2 stub — `on_join` / `on_leave`

```python
def on_join(self, player: Player) -> None:
    """Called (lock held) when a player registers.  D2: tell the controller."""

def on_leave(self, player: Player, reason: str) -> None:
    """Called (lock held) when a player leaves or times out.  D2: tell the controller."""
```

**Both bodies are empty.** The call sites are real (`server.py:139` and `server.py:162`), and the
docstrings say exactly what should go there. **This is the single biggest gap between the Team 11
documents and the code.** File 06 §3.1 explains why, and what it would take to close it.

### The CSV log

Opened in `__init__` (`server.py:68-72`), with the header:

```python

```

and one row per received `STATE_UPDATE`:

```python

```

**The `kind` column** (`new` / `late` / `duplicate` / `stale`) is what makes the loss analysis

### The CLI

```
usage: python3 -m game.server [-h] [--host HOST] [--port PORT] [--log LOG]
                              [--drop DROP] [--stats-interval STATS_INTERVAL]
```

| Flag | Default | Meaning |
|---|---|---|
| `--host` | `0.0.0.0` | Listen address. **`0.0.0.0` is correct for a multi-laptop demo.** |
| `--port` | `5000` | UDP port. |

### Suspicious / noteworthy
- **`self.sock.settimeout(0.2)`** means the recv loop wakes 5×/s even when idle. Trivial CPU
  cost, and it is what makes `Ctrl-C` responsive.
- **`_send` swallows `OSError`** (`server.py:188-192`). On UDP, `sendto` can fail with
  `ECONNREFUSED` if a previous packet triggered an ICMP port-unreachable. Swallowing it is the
  right call — the game should not die because one client vanished.
- **The server is a single point of failure.** If it stops, every client freezes on its last
  snapshot. Not a bug — a design limitation, and it is documented.
- **No authentication.** Anyone who can reach UDP 5000 can take a slot. File 05 §7 lists this.
- **No bug found in the logic.** The only gap is the deliberate D2 stub.

## 8. `game/client.py` — one player (human or bot)

**Path:** `game/client.py` · 287 lines · `[EXEC]` as `python3 -m game.client`.

### What it does
Joins a server, sends its paddle direction, receives the world, and (optionally) draws it.

**The core design idea is in the docstring:**

> *"The network part (GameClient) knows nothing about how the paddle is controlled: it just
> calls `input_fn(snapshot, slot) -> -1/0/+1` every tick."*

That is why a bot and a human are interchangeable.

### The socket setup

```python
self.addr = (socket.gethostbyname(server), port)
self.sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
self.sock.bind(("", 0))            # OS picks a free ephemeral port
self.sock.settimeout(0.2)
```

| Line | Why |
|---|---|
| `gethostbyname(server)` | Resolves **once**, at construction. A hostname that fails to resolve here fails immediately with `socket.gaierror`. |
| `bind(("", 0))` | **Ephemeral port.** The client never needs a well-known port — the server learns the address from the first packet. This is what makes the firewall setup simple. |
| `settimeout(0.2)` | Same reason as the server — responsive shutdown. |

### Joining — `join()`

```python
for attempt in range(1, self.join_retries + 1):
    self._send(P.encode(P.JOIN, 0, 0))
    deadline = time.monotonic() + self.join_timeout
    while time.monotonic() < deadline:
        try:
            data, addr = self.sock.recvfrom(2048)
        except socket.timeout:
            continue
        if addr != self.addr:
            continue
        hdr, _ = P.decode(data)
        if hdr.msg_type == P.JOIN_ACK:
            if hdr.player_id == C.NO_PLAYER:
                raise JoinError("server is full")
            self.player_id = hdr.player_id
            return self.player_id
    log.info("no JOIN_ACK (attempt %d/%d)", attempt, self.join_retries)
raise JoinError("no reply from server %s:%d" % self.addr)
```

| Constant | Value | Meaning |
|---|---|---|
| `JOIN_RETRIES` | 3 | How many `JOIN` packets to send |
| `JOIN_TIMEOUT` | 0.5 s | How long to wait for the `JOIN_ACK` each time |

So a failed join takes about **1.5 seconds** before it gives up. Two different error messages,
and they mean different things:

| Message | Cause | Fix |
|---|---|---|
| `could not join: server is full` | 4 players already registered | Wait 3 s, or press `Q` in a game |
| `could not join: no reply from server X:5000` | Nothing answered | Wrong IP, firewall, or Wi-Fi isolation (file 05 §5.1) |

**Why `addr != self.addr` is safe:** the server replies from the same socket it received on, so
the source address is the server's IP and port. On a multi-homed host the kernel might pick a
different source IP — in that case the client would silently ignore the reply. This is a real
(if unlikely) limitation; file 05 §7 lists it.

### The two loops

**`_send_loop`** (30 Hz): asks the input function for a direction, and sends a `STATE_UPDATE`:

```python
direction = 0
if self.input_fn:
    try:
        direction = self.input_fn(self.get_snapshot(), self.player_id)
    except Exception:
        direction = 0
self._send(P.encode(P.STATE_UPDATE, self._update_seq, self.player_id, P.pack_update(direction)))
self._update_seq += 1
```

The `try/except` around the input function means a crash in the UI or the bot cannot kill the
network thread.

**`_recv_loop`**: handles three message types.

```python
if hdr.msg_type == P.STATE_BROADCAST:
    snap = P.unpack_broadcast(payload)
    kind, _gap = self.tracker.observe(hdr.seq)
    if self._log_csv:
        self._log_csv.writerow([kind, "%.6f" % t_recv, hdr.seq, "%.6f" % hdr.send_time])
    if kind == NEW:                    # only the newest state is ever shown
        with self._lock:
            self._snapshot = snap
            self._last_rx = time.monotonic()
elif hdr.msg_type == P.PONG:
    echoed = P.unpack_echo(payload)
    self.rtt = t_recv - echoed
    self._rtt_sum += self.rtt
    self._rtt_n += 1
    if self._log_csv:
        self._log_csv.writerow(["pong", "%.6f" % t_recv, hdr.seq, "%.6f" % echoed])
```

**This is the "latest state wins" rule on the client.** A `LATE` broadcast is **not** applied —
it is old news. But it **is** counted as received, so the loss statistics stay correct.

**The RTT calculation:** `self.rtt = t_recv - echoed`. The server put the client's original
`send_time` into the `PONG` payload, so subtracting it from the arrival time gives the true
round trip **without needing synchronised clocks**. That is why RTT is the number to quote
across real machines.

### `leave()` — the clean exit

```python
def leave(self):
    self._stop.set()
    for t in self._threads:
        t.join(timeout=2)
    if self.player_id is not None:
        for _ in range(2):                        # one retry, LEAVE is cheap
            self._send(P.encode(P.LEAVE, 0, self.player_id))
    try:
        self.sock.close()
    except OSError:
        pass
    if self._log_file:
        self._log_file.close()
        self._log_file = None
```

**The `LEAVE` packet is sent twice.** UDP is unreliable, so a single `LEAVE` could be lost and
the server would hold the slot for the full 3-second timeout. Two cheap packets make it almost
certain to arrive. **Good engineering — worth mentioning in the viva.**

### The two-step rendering trick

This is the cleverest part of the UI and it is worth understanding:

1. **`render_pixels()`** draws into a **pixel buffer** — a 2-D list of ints, one per pixel.
   The game logic only knows about this buffer.
2. **`to_cells()`** converts the pixel buffer into **terminal character cells** — each cell is
   two pixels tall, so a 72×72 pixel arena becomes 36 rows × 72 columns. It also merges runs of
   the same colour into a single `(text, colour)` pair so the screen does not flicker.

**Why two steps?** Because the arena has to be **square** (a pong arena is square), but a
terminal character cell is **twice as tall as it is wide**. Rendering to pixels first and then
compressing vertically gives a square arena that still fits the character grid.

## 11. `sdn/baseline_switch.py` — the control (baseline) controller

**Path:** `sdn/baseline_switch.py` · 74 lines · `[EXEC]` as a Ryu app.

### What it does
A plain **OpenFlow 1.3 layer-2 learning switch**. It is the **control** for every experiment.

The docstring states the experimental design:

> *"This is the control for every experiment: it forwards everything the same way and knows
> nothing about the game. qos_switch.py subclasses it, so the two controllers forward
> identically and differ ONLY in queue selection - a fair comparison."*

**That is the single most important sentence in the SDN half of the project.** Because the
priority controller **subclasses** the baseline, the two differ by exactly one method. Any
difference in the measured results cannot be blamed on a different forwarding behaviour.

### The OpenFlow version

```python
OFP_VERSIONS = [ofproto_v1_3.OFP_VERSION]
```

**OpenFlow 1.3**, which is what the assignment asks for. OVS speaks it natively.

### The two priorities

```python
PRIO_TABLE_MISS = 0
PRIO_FORWARD = 10
```

| Priority | Rule | Meaning |
|---|---|---|
| 0 | empty match | "I do not know this flow" — send it to the controller |
| 10 | `eth_dst=<mac>` | "I know where this goes" — forward to that port |

### The table-miss rule — `_on_features`

```python
@set_ev_cls(ofp_event.EventOFPSwitchFeatures, CONFIG_DISPATCHER)
def _on_features(self, ev):
    dp = ev.msg.datapath
    ofp, parser = dp.ofproto, dp.ofproto_parser
    actions = [parser.OFPActionOutput(ofp.OFPP_CONTROLLER, ofp.OFPCML_NO_BUFFER)]
    self.add_flow(dp, PRIO_TABLE_MISS, parser.OFPMatch(), actions)
    self.logger.info("switch %016x connected (%s)", dp.id, type(self).__name__)
```

This fires when a switch connects. It installs the **catch-all, lowest-priority rule** that
sends anything the switch does not recognise to the controller.

`OFPCML_NO_BUFFER` means "do not buffer this packet in the switch — I will send the full packet
with the `PacketOut`". That is the simple, correct choice for a small demo topology.

**The log line you see in the VM:**

```
switch 0000000000000001 connected (BaselineSwitch)
```

**This line only appears after the topology starts.** Before that, the controller looks hung —
it is not. This is the single most common "is it broken?" moment. File 03 §6.1 calls it out.

### The learning logic — `_on_packet_in`

```python
eth = packet.Packet(msg.data).get_protocols(ethernet.ethernet)[0]
if eth.ethertype == ether_types.ETH_TYPE_LLDP:
    return
table = self.mac_to_port.setdefault(dp.id, {})
table[eth.src] = in_port              # learn: src MAC is on this port
out_port = table.get(eth.dst, ofp.OFPP_FLOOD)   # look up dest, else flood

if out_port != ofp.OFPP_FLOOD:
    self.install_forwarding(dp, eth.dst, out_port)   # <-- the subclass hook

data = msg.data if msg.buffer_id == ofp.OFPP_NO_BUFFER else None
dp.send_msg(parser.OFPPacketOut(datapath=dp, buffer_id=msg.buffer_id, in_port=in_port,
                                actions=[parser.OFPActionOutput(out_port)], data=data))
```

| Step | What it does |
|---|---|
| `eth.ethertype == ETH_TYPE_LLDP` → `return` | **Ignores LLDP.** This is important — Mininet's switches send LLDP keepalives, and without this the controller would learn LLDP MACs and install junk rules. |
| `table[eth.src] = in_port` | Learns the source MAC → port mapping, per switch (`dp.id`). |
| `table.get(eth.dst, OFPP_FLOOD)` | If the destination is unknown, flood it to all ports. |
| `install_forwarding(...)` | **Only called once the destination is known.** This is the subclass hook. |
| `OFPPacketOut` | Forwards the packet immediately, so the very first packet of a flow is not delayed waiting for a round trip to the controller. |

**The `install_forwarding` hook is the whole experimental design.** The baseline implements it
as "output to the port". The priority controller overrides it to "output to the port, but set
the queue first".

### `add_flow()` — the FlowMod

```python
def add_flow(self, dp, priority, match, actions, idle_timeout=0):
    ofp, parser = dp.ofproto, dp.ofproto_parser
    inst = [parser.OFPInstructionActions(ofp.OFPIT_APPLY_ACTIONS, actions)]
    dp.send_msg(parser.OFPFlowMod(datapath=dp, priority=priority, match=match,
                                  instructions=inst, idle_timeout=idle_timeout))
```

**Every rule in the project is written through this one function.** It is a 4-line wrapper
around `OFPFlowMod` — `APPLY_ACTIONS` means "do these actions and continue".

`idle_timeout=0` means the rules never expire. For a demo that is the right choice (no rule
churn during a 15-second measurement).

### Dependencies
`ryu.base.app_manager`, `ryu.controller.ofp_event`, `ryu.controller.handler`,
`ryu.lib.packet`, `ryu.ofproto.ofproto_v1_3`. **All of these require the Ryu virtualenv.**

### Suspicious / noteworthy
- **The file has a `# -*-` style comment requirement**: *"Runs under the Ryu environment
  (Python 3.9): keep the syntax 3.9-compatible."* That is why the whole project avoids
  `match` statements and `X | Y` type unions.
- **The learning table is in RAM only.** Restarting the controller wipes it, and the switches
  keep their old rules. `topology.py` recreates the network for each scenario, so this does
  not bite in practice.
- **`install_forwarding` is called on every packet** until the destination is learned. After
  that, the switch handles the flow in hardware and the controller is not involved. **This is
  the whole point of an SDN learning switch** and a good thing to explain.
- **No bug.** Clean, small, and the base class for the priority controller.

## 12. `sdn/qos_switch.py` — the priority controller

**Path:** `sdn/qos_switch.py` · 45 lines · `[EXEC]` as a Ryu app.

### What it does
**The same learning switch, plus a queue decision.**

The docstring gives the complete rule set:

```
priority 20   UDP port 5000 (either direction)   ->  set_queue 1 (game)   + output
priority 10   everything else                    ->  set_queue 2 (other)  + output
```

### It is only 45 lines, because it overrides exactly one method

```python
from game import config as C
from sdn.baseline_switch import PRIO_FORWARD, BaselineSwitch

PRIO_GAME = 20
ETH_TYPE_IP = 0x0800
IP_PROTO_UDP = 17


class QosSwitch(BaselineSwitch):
    def __init__(self, *args, **kwargs):
        super(QosSwitch, self).__init__(*args, **kwargs)
        self.logger.info("QoS: UDP port %d -> queue %d, everything else -> queue %d",
                         C.GAME_PORT, C.QUEUE_GAME, C.QUEUE_BG)

    def install_forwarding(self, dp, dst_mac, out_port):
        parser = dp.ofproto_parser
        output = parser.OFPActionOutput(out_port)

        # everything else: low-priority queue
        self.add_flow(dp, PRIO_FORWARD, parser.OFPMatch(eth_dst=dst_mac),
                      [parser.OFPActionSetQueue(C.QUEUE_BG), output])

        # game traffic, both directions
        for field in ("udp_src", "udp_dst"):
            match = parser.OFPMatch(eth_dst=dst_mac, eth_type=ETH_TYPE_IP, ip_proto=IP_PROTO_UDP,
                                    **{field: C.GAME_PORT})
            self.add_flow(dp, PRIO_GAME, match, [parser.OFPActionSetQueue(C.QUEUE_GAME), output])
```

### The three rules it installs, per destination

| Priority | Match | Actions |
|---|---|---|
| **20** | `eth_dst=<mac>`, `eth_type=0x0800` (IPv4), `ip_proto=17` (UDP), `udp_dst=5000` | `set_queue:1`, `output:<port>` |
| **20** | `eth_dst=<mac>`, `eth_type=0x0800`, `ip_proto=17`, `udp_src=5000` | `set_queue:1`, `output:<port>` |
| **10** | `eth_dst=<mac>` (catch-all for this destination) | `set_queue:2`, `output:<port>` |

**Why two rules for the game traffic?** Because the game traffic flows in **both directions**:

- Client → server: the **destination** port is 5000 → matched by `udp_dst=5000`.
- Server → client: the **source** port is 5000 → matched by `udp_src=5000`.

The comment in the source says exactly that: *"game traffic, both directions (client -> server
uses dst port, server -> client src port)"*.

**Why priority 20 beats priority 10:** OpenFlow evaluates rules in **descending priority
order**, and the first match wins. So the game rules are checked first, and the catch-all only
fires for traffic that is not the game.

### The port number comes from `game/config.py`

```python
C.GAME_PORT    # 5000
C.QUEUE_GAME   # 1
C.QUEUE_BG     # 2
```

**This is the coupling point between the application and the network.** The controller reads
the same constant the game uses. Change `GAME_PORT` in one place and the controller follows.

This works because `game/config.py` is deliberately **import-free and Python 3.9-clean** — the
Ryu virtualenv is Python 3.9 and can import it safely. It is the **only** project file the
controller imports.

### The startup log line

```
QoS: UDP port 5000 -> queue 1, everything else -> queue 2
```

and per switch:

```
switch 0000000000000001: aa:bb:cc:dd:ee:ff is behind port 3 (game -> queue 1)
```

### The limitation — the rules are static

**This controller installs its rules when the switch connects and then never changes them.**
There is no port-statistics polling, no re-shaping, no reaction to congestion.

The Team 11 document promised: *"the controller checks port statistics regularly. If the link
is congested by background traffic, it limits the background traffic so game packets are not
delayed."*

**What actually achieves that outcome:** `topo/topology.py --qos priority` creates the HTB
classes with a **hard 1 Mbit/s ceiling on the background queue**. The game queue therefore
never has anything to wait behind. The *outcome* is achieved; the *mechanism* is static.

File 06 §3.2 has the full wording to use in the viva.

### Suspicious / noteworthy
- **`set_queue` on a port without queues is ignored.** The docstring says this: *"Ports without
  those queues ignore set_queue."* So the controller is safe to run on a topology with no QoS
  configuration — the rules install fine and simply have no effect.
- **The rules are per destination MAC**, not per port. So the switch installs a rule set for
  each MAC it learns. With 7 hosts that is ~21 rules per switch. **The match includes
  `eth_dst`**, which is why the priority rules are more specific than the catch-all.
- **The `__init__` log line prints before any switch connects.** That is why you see it
  immediately when starting the controller.
- **No bug.** 45 lines, one overridden method, and it produces the project's headline result.

## 13. `topo/topology.py` — the Mininet network

**Path:** `topo/topology.py` · 411 lines · `[EXEC]` as `sudo python3 -B topo/topology.py ...`.

### What it does
Builds the virtual network, shapes the bottleneck link, starts the game server and the bots
inside it, floods it with background traffic, and prints the results.

### The topology

```
        PLAYER SIDE (s1)                          SERVER SIDE (s2)
        ───────────────────                        ───────────────────
        h1   10.0.0.1   player                     hs   10.0.0.10   game server
        h2   10.0.0.2   player
        h3   10.0.0.3   player                     hb2  10.0.0.11   iperf3 sink
        h4   10.0.0.4   player
        hb1  10.0.0.5   iperf3 source
                     │
                     └── s1 ══════ 10 Mbit/s bottleneck ══════ s2
```

| Constant | Value |
|---|---|
| `SERVER_IP` | `10.0.0.10` |
| `PLAYERS` | `["h1", "h2", "h3", "h4"]` |
| `PLAYER_SIDE` | `["h1", "h2", "h3", "h4", "hb1"]` — attached to `s1` |
| `SERVER_SIDE` | `["hs", "hb2"]` — attached to `s2` |
| `BOTTLENECK_BPS` | `10_000_000` (10 Mbit/s) |
| `GAME_MIN_BPS` | `4_000_000` — the game queue's guarantee |
| `BG_MIN_BPS` | `1_000_000` — the background queue's guarantee |

**The addressing is hard-coded** and does not depend on your physical network. It matches the
Team 11 design: *"a game server, 3–4 player hosts, and 1–2 hosts for background traffic,
connected through OVS switches with one limited-bandwidth link."*

### `cleanup_stale()` — the hand-written Mininet cleanup

```python
def cleanup_stale():
    subprocess.run(["pkill","-9","-f","^bash --norc --noediting -is mininet:"], ...)
    for br in ("s1","s2"):
        subprocess.run(["ovs-vsctl","--if-exists","del-br",br], ...)
    links = subprocess.run(["ip","-o","link","show"], ...).stdout
    for name in set(re.findall(r"\b((?:h[1-4]|hb[12]|hs|s[12])-eth\d+)\b", links)):
        subprocess.run(["ip","link","del",name], ...)
```

**This is deliberately NOT `sudo mn -c`.** Mininet's cleanup does `killall ryu-manager`, which
kills the controller. This function:

1. Kills **stale Mininet host shells** only (matched by their exact command line).
2. Deletes **only the `s1` and `s2` bridges** — not other OVS bridges on the machine.
3. Deletes **leftover veth interfaces** matching the project's own naming pattern.

**It never touches `ryu-manager`.** This is a genuinely thoughtful piece of engineering and
worth mentioning in the viva.

### `build()` — the network

```python
switch = partial(OVSSwitch, failMode=fail_mode, protocols="OpenFlow13", datapath=datapath)
net = Mininet(controller=None, switch=switch, link=Link, autoSetMacs=True, waitConnected=False)
if controller == "remote":
    net.addController("c0", controller=RemoteController, ip=controller_ip, port=controller_port)
```

| Setting | Value | Why |
|---|---|---|
| `failMode` | `standalone` if no controller, `secure` if remote | With a remote controller, a switch that loses it goes into "secure" mode and drops traffic instead of learning by itself. **This is what makes the SDN experiment honest** — the forwarding really is being done by the controller. |
| `protocols` | `OpenFlow13` | OpenFlow 1.3, as the assignment requires. |
| `datapath` | `kernel` by default, `user` as a fallback | The kernel datapath is faster. `--datapath user` works without the OVS kernel module. |
| `autoSetMacs=True` | — | Unique MACs per host, so the learning switch does not confuse them. |
| `waitConnected=False` | — | The script does its own `waitConnected(timeout=20)` later, so it can print a helpful error. |

### `disable_offloads()` — why this matters

```python
node.cmd("ethtool -K %s tso off gso off gro off tx off rx off 2>/dev/null" % intf.name)
```

The docstring explains it:

> *"Mininet's virtual links otherwise carry 64 KB 'super packets' that no real link would, which
> distorts queueing at the bottleneck (and makes TCP stall on the OVS userspace datapath)."*

**Without this, the measurement is wrong.** TSO/GSO/GRO let the kernel build a 64 KB packet out
of many small ones, so a queue never fills up the way it would on a real link. The bottleneck
would look faster and less congested than it is. If `ethtool` is missing, the script prints a
warning and continues — **so check that warning appeared or did not.**

### `configure_qos()` — the three QoS modes

| Mode | What it creates |
|---|---|
| `none` | No shaping at all. The link runs at line rate. |
| `plain` | One HTB class, `max-rate = 10 Mbit/s`. **The baseline.** One FIFO queue for everything. |
| `priority` | HTB with **two queues** on top of the 10 Mbit/s limit. |

**The priority mode's `ovs-vsctl` command, unpacked:**

```
create qos type=linux-htb other-config:max-rate=10000000
create queue other-config:min-rate=4000000 other-config:max-rate=10000000 other-config:priority=0
create queue other-config:min-rate=1000000 other-config:max-rate=10000000 other-config:priority=1
```

| Queue | Priority | Min rate | Max rate | Traffic |
|---|---|---|---|---|
| **1** | 0 (higher) | 4 Mbit/s | 10 Mbit/s | game (UDP 5000) |
| **2** | 1 (lower) | 1 Mbit/s | 10 Mbit/s | everything else |

**HTB's `min-rate` is a *guarantee*.** Queue 2 is **guaranteed** 1 Mbit/s, and since the link
total is 10 Mbit/s, queue 1 can use the remaining 9 Mbit/s.

**But the crucial part is that queue 2's actual share stays at 1 Mbit/s** — the background
flood cannot take more than that, because the queue's `max-rate` is effectively bounded by the
link and its guaranteed share. The excess is dropped at the queue.

**This is why the game delay collapses to 0.13 ms.** The background traffic is *starved*, not
merely deprioritised.

**The wait loop after configuring** is important:

```python
deadline = time.time() + 5
while "htb" not in subprocess.run(["tc","qdisc","show","dev",port], ...).stdout:
    if time.time() > deadline:
        raise RuntimeError("QoS did not appear on %s (no htb qdisc after 5 s)" % port)
    time.sleep(0.2)
```

`ovs-vswitchd` applies the QoS config **asynchronously**. Without this wait, the diagnostics
would run before the qdisc exists and the counters would be empty.

### `run_smoke()` — the automated end-to-end check

This is the "one command proves it works" entry point. In order:

1. Start the game server on `hs`.
2. Wait 1 s.
3. Start 4 bots, one per player host, each with a **different seed** (`seed=i+1`).
4. If `--bg-mbps` was given: wait 1.5 s (so every bot has joined), then start the background flood

5. Wait for all the bots to finish.
6. Stop everything.
7. Read each `h*.csv` with `metrics.summarize_client()` and print the table.
8. Read `server.csv` and add the per-player rows.

**The pass/fail rule** (`topology.py:397-401` region):

```python
status = 0 if (drop == 0 and shaped_ok and game_ok) else 1
```

| Check | Rule |
|---|---|
| `drop == 0` | `net.pingAll()` dropped no packets |
| `shaped_ok` | The measured iperf throughput is between **60 % and 105 %** of the configured rate |
| `game_ok` | Every player has a usable log, and (in an uncongested run) at least 80 % of the expected packets arrived and loss is under 5 % |

**Note the special case for a congested run:** *"congested run: loss is the result, not a
failure"*. In a `--bg-mbps` run, the check is relaxed to just "there is a log with data" —
because loss is expected and is the thing being measured.

### The matrix

## 16. `analysis/metrics.py` — turning CSVs into numbers

**Path:** `analysis/metrics.py` · 148 lines · `[IMPORT]` by `topo/topology.py`,
`topo/run_scenario.py`, `analysis/report.py`, `tests/test_metrics.py`.

### What it does
Reads the CSV logs and computes **delay, jitter, loss, and RTT**.

**Standard library only** — so it runs on the Mac and in the VM. The docstring says so.

### The definitions (from the docstring)

```
delay   one-way delay in ms = recv_time - send_time.  Valid because every Mininet
        host shares the same kernel clock (time.monotonic).
jitter  mean absolute difference between the delays of consecutive arrivals (ms).
loss    1 - (unique packets received) / (highest seq - lowest seq + 1).
        Late (out-of-order) packets count as received; duplicates are ignored.
rtt     PING -> PONG round trip in ms (client logs only).
```

### The key line — which kinds count as "arrived"

```python
ARRIVED = ("new", "late")
```

**This is the correctness rule for the loss number.** A `late` packet *did* arrive — it was just
out of order — so it must count as received. A `duplicate` was already counted. Only packets
that never showed up are lost.

### `summarize()` — the core function

```python
recv_times = [r[1] for r in rows]
t_min, t_max = min(recv_times), max(recv_times)
t_start = t_min + warmup
t_end = t_max - tail

seqs = set()
delays = []
for kind, recv, seq, send in rows:
    if warmup > 0 and recv < t_start:   continue
    if tail > 0 and recv > t_end:       continue
    if kind in ARRIVED:
        seqs.add(seq)
        delays.append((recv - send) * 1000.0)
```

**The warm-up / tail trimming is based on `recv_time`,** not on the row index. That is correct —
the measurement window is a *time* window.

**Note `seqs` is a set, not a list.** A `late` packet that fills a gap is counted once, and a
duplicate is never counted twice. And `expected` is computed from the **sequence numbers**, not
from the packet count:

```python
n = len(seqs)
expected = (max(seqs) - min(seqs) + 1) if seqs else 0
lost = expected - n
```

**This is the right way to compute loss.** If you counted rows instead, a duplicate would look
like an extra packet and the loss percentage would go negative.

### The jitter formula

```python
jitter = (sum(abs(b - a) for a, b in zip(delays, delays[1:])) / (len(delays) - 1)) if len(delays) > 1 else 0.0
```

**The mean absolute difference between consecutive delays.** This is the RFC 3550 style
"inter-arrival jitter" but computed on the *delay* rather than on the arrival timestamp. It is
the standard classroom definition and it is what the report uses.

**Note it is computed on the delays *in arrival order*, not sorted.** That is correct — jitter
is about how much the delay changes from one moment to the next.

### The percentile function

```python
def _percentile(sorted_vals, p):
    if not sorted_vals: return 0.0
    k = (len(sorted_vals) - 1) * p / 100.0
    lo = int(k)
    hi = min(lo + 1, len(sorted_vals) - 1)
    return sorted_vals[lo] + (sorted_vals[hi] - sorted_vals[lo]) * (k - lo)
```

**Linear interpolation between the two nearest ranks.** The p95 is the value below which 95 % of
the samples fall — the "worst 5 %" that a player would actually notice as a stutter.

### Reading the two CSV formats

| File | Header | Read by |
|---|---|---|
| Client `h1.csv` | `kind,recv_time,seq,send_time` | `read_client_csv()` — returns `(rows, rtts)` |
| Server `server.csv` | `recv_time,player,seq,send_time,kind` | `read_server_csv()` — returns `{slot: rows}` |

**The client log also contains `pong` rows**, which is where the RTT comes from:

```python
if r["kind"] == "pong":
    rtts.append((recv - send) * 1000.0)
```

### `main()` — the CLI

```python
for path in paths:
    with open(path, newline="") as f:
        first = f.readline().split(",")[0].strip()
    name = path.rsplit("/", 1)[-1]
    if first == "kind":                      # client log
        entries.append((name, summarize_client(path)))
    else:                                    # server log: one stream per player
        for slot, s in summarize_server(path).items():
            entries.append(("%s [P%d up]" % (name, slot + 1), s))
```

**It sniffs the format by looking at the first column name.** `"kind"` means a client log;
anything else means a server log, which is then split into one stream per player.

**With no arguments it prints the docstring and returns exit code 1.**

### Suspicious / noteworthy
- **`delay_p50_ms` is computed but never shown in the table.** It is in the dict, so it is
  available, but `format_table()` shows mean / p95 / max. Not a bug — just unused.
- **The RTT is in ms here, in seconds in `GameClient.stats()`.** Two units, two places.
- **The "no usable log" case is handled by the callers**, not here — `topology.py` catches
  `(OSError, KeyError, ValueError)` and prints a message pointing at the `.out` file.
- **No bug.** 7 tests cover it.

## 17. `analysis/report.py` — aggregation and the markdown report

### `mean_std()`

```python
def mean_std(values):
    n = len(values)
    if n == 0: return 0.0, 0.0
    m = sum(values) / n
    if n < 2: return m, 0.0
    var = sum((x - m) ** 2 for x in values) / (n - 1)
    return m, math.sqrt(var)
```

**This is the sample standard deviation** (divides by `n - 1`, not `n`). That is the correct
choice for a small sample — it estimates the population spread from a few repeats.

**With one repeat the std is 0.0.** That is why the current `results/aggregate.csv` shows
`std = 0.000` everywhere — there is only one run per cell so far. **Say this out loud in the

## 17. `scripts/clean_results.py` — result directory cleanup

**Path:** `scripts/clean_results.py` · 78 lines · `[EXEC]`
Executed as `python3 scripts/clean_results.py [--dry-run | --keep DAYS | --all]`.

### What it does
Safely cleans old experiment runs from `results/raw/` so the repository does not fill up with hundreds of megabytes of CSV packet logs.

### Key flags
- `--dry-run`: Prints what would be deleted without deleting anything. Always use first!
- `--keep N`: Keeps raw directories modified within the last N days (default: 7 days).
- `--all`: Completely wipes all raw folders, `summary.csv`, `run_state.json`, and graphs.
